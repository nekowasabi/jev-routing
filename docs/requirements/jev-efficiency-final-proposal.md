# jev-routing 最終改善案

作成日: 2026-09-19。対象: 調査時の `24c7276` と未コミット変更。
本書は調査・互換性レビュー・Grokの再現検証を統合した改善方針であり、実装済みの報告ではない。

## 結論

**「Jevへ移す処理を増やす」ことより、正しい情報とツールを維持しながら、LLMの不要な往復とJevへの不要な問い合わせを減らすことを優先する。**

実施順序は、**①互換性・情報保持の修正 → ②効果を測れる状態にする → ③圧縮・ツール限定・推論設定を個別に比較する → ④不要な判定を省く → ⑤結果選別を広げる**とする。

Claude CodeとGrok Buildを最初の実運用検証対象にする。CodexはResponses履歴対応を同じ基礎修正に含め、実経路確認後に検証対象へ加える。Cursor・Devinは、設定項目があるだけで最適化対応済みとは扱わない。

## 判断の根拠

| 確認できたこと | 改善案への反映 |
|---|---|
| Claude/Grokの並列ツール結果が別の行動に紐づく | 結果選別や並列化の拡大より、呼出しIDの対応を先に直す |
| GrokのBash・Agent対応名が確認した実カタログと異なる | ホスト固有の名前対応を修正し、ローカル選択が機能するようにする |
| Responsesの呼出し・結果が行動履歴に入らない | Codexでは圧縮・工程判定の前提から直す |
| 目的変更後も圧縮判定が再利用される | キャッシュを高速化する前に再利用条件を正す |
| Jevへ送る入れ子の結果が入力予算を超えたまま残る | 送信前の予算検査を実効化し、超過時に無理に送らない |
| Claudeの測定には、本文が減ってもターン・時間・報告費用が増える例がある | 本文削減率を主目的にせず、タスク全体で評価する |
| プロキシ通過・最適化適用・Jev実呼出し・成果の正しさが混同されている | 計測を分離し、効果のない経路を「対応済み」と表示しない |

Grokの旧比較はベンチマークの完了文字列を満たしていない。これは比較を無効とする根拠だが、タスク全体が失敗した原因を単一スキーマ化に断定する根拠ではない。ターン増加の原因も未確定であり、以下の比較実験で切り分ける。

## ① 最初に実装する修正

この段階の目的は正しい最適化の土台を作ること。単独での高速化を保証するものではない。

| 優先 | 修正内容 | 最小の実装方針 | 合格条件 |
|---|---|---|---|
| 最優先 | 呼出しと結果の対応 | 既存の内部表現を使い、呼出しIDで結合する。未知IDを直前の呼出しへ代入しない | Claude/Grokの並列・順不同・未知ID・欠損結果で誤対応しない |
| 最優先 | Grokの名前対応 | 既存のホスト対応表と別名処理を実カタログに合わせる。既存名の互換性も確認する | `run the tests` と委譲課題が期待するローカル工程を通る |
| 最優先 | Responses履歴 | `function_call` / `function_call_output` を既存の呼出し・結果表現へ変換する | 実行済みの検索・読取を認識し、次工程を最初からやり直さない |
| 高 | 不確実な圧縮結果 | 通信失敗、欠損回答、不正な評価と、有効な低評価を区別する。不確実なら保持し、削除判定として保存しない | 不正・部分回答で必要な履歴が消えない |
| 高 | 判定キャッシュ | まず完全な評価入力が同じ場合だけ再利用する。目的・内容・規則の変更を無視した再利用を止める | 目的変更や内容変更で古い判定を再利用せず、同じ入力の再送は再利用できる |
| 高 | 入力予算 | 入れ子を含む実際の送信内容を短縮・再検査する。収まらなければ外部判定を省き、安全な既存経路へ戻す | 予算超過のまま送信しない。短縮のためにユーザー制約を失わない |
| 高 | 要求の意味の維持 | 強制 `tool_choice` や未対応の推論設定を勝手に変更しない。対応できない要求は原形を保つ | ツール強制、認証、ストリーミング等の契約を保持する |

Grokが隔離環境に作成した再現テストを必要最小限に整理して回帰テストへ取り込む。失敗を消すために期待値を現状の誤動作へ合わせない。既存の `internal/host`・`plan`・`proxy`・`compact`・`jev` 内で対応し、汎用の新しい抽象層は作らない。

## ② 計測をタスク全体へ改める

既存の統計と比較スクリプトを拡張し、専用の計測基盤は新設しない。

| 分けて記録するもの | 必要な理由 |
|---|---|
| プロキシ到達、変換対象、実際の変換、素通し理由 | Cursorのような「到達したが最適化は未適用」を識別する |
| ローカル判定、Jev実呼出し、キャッシュ再利用、失敗・代替処理 | `engine=live` を実呼出しと誤認しない |
| LLMの親子合計の入力・出力・推論・キャッシュ使用量と呼出し回数 | 本文が減っても追加ターンで総使用量が増えるケースを検出する |
| タスク総時間、Jev待ち、上流待ち、ツール実行時間 | どの変更が全体を速くしたか判断する |
| 圧縮した結果のID、保持・切詰め・削除の別、再検索・再読 | 圧縮後に失った情報を取り直していないか確認する |
| 成果物・テスト・必要な証拠による完了判定 | `CHECK: PASS` の自己申告や表記揺れに依存しない |

JSONのバイト差は補助指標に留める。Jevの使用量や費用が取得できない場合は欠測とし、上流LLMの費用だけを総費用と呼ばない。APIごとの使用量項目の重複計上も避ける。

比較にはコミットだけでなく、未コミット差分またはソース指紋、利用バイナリ、ホスト・モデル・設定を記録する。生の認証情報は保存しない。

## ③ 圧縮・ツール限定・推論設定を個別に比較する

**最初から複数の変更をまとめて入れない。** 修正後の基準実装に対し、一度に一つの条件だけを変える。

| 比較 | 確かめる仮説 | 採用する条件 |
|---|---|---|
| 圧縮あり／なし／重要な結果を保持 | 圧縮が証拠の再取得や追加ターンを生んでいないか | 証拠と完了品質を保ち、再取得を含む総使用量・総時間が改善する |
| 単一候補／工程に必要な少数候補／元カタログ | 候補限定が次工程への切替えや異なるツールの一括利用を妨げていないか | スキーマ量だけでなく、ターン数とタスク全体で改善する |
| ホストの推論設定を保持／現行の削減設定 | 推論削減が計画の質を落とし、追加ターンを増やしていないか | 推論・出力の増減を含む総量と総時間で改善する |

圧縮では、未解決エラー、回答に必要な証拠、最新の検証結果を保護する。機械的に保護できる状態はコードで扱い、意味的に必要か確信できない場合は残す。「何度も使われていない」という理由だけで捨てない。

少数候補化には既存の候補情報を使う。ただし、同じツールが続いたことを根拠に次も同じツールへ固定しない。同じツールの複数呼出しは単一スキーマでも可能な場合があるため、「1スキーマだから並列実行できない」とは仮定しない。

推論設定はホスト・モデルの契約に従う。Claude、Grok、Codexへ同じ値を一律適用しない。元の設定保持を比較条件に入れ、どちらが有利かは測定で決める。

## ④ 不要なJev問い合わせとローカル処理を省く

基礎修正と計測の後に、次を小さく実施する。

- 削減可能な結果がない、または既に十分小さい要求では圧縮判定を行わない。閾値は結果の件数だけで決めず、削減量と追加待ち時間を測って決める。
- 正しく再利用できるキャッシュがある場合、不要な状態整形や外部通信を省く。
- 履歴を短くするたびに全体を再生成・再計数する処理を減らす。
- 新しい結果を含むローカル判定で次の動作が十分確実な場合だけ、外部の次ツール判定を省く。これは既存の確信度による分岐を活用する。

「直前と同じツールだから外部判定を省き、そのツールを維持する」近似は採用しない。結果を受けて別ツールへ切り替える必要を見落とすためである。新たな会話ID管理や長寿命の選択キャッシュも、この段階では追加しない。

## ⑤ 新しいJev用途は、短い結果候補の選別から始める

初期の追加用途は、検索結果・読取結果・検証ログのうち、次のLLM判断に必要な候補を選ぶことに限定する。

処理の流れは、**ローカルで重複排除・構造化 → 短い候補だけJevへ提示 → 必要な本文と出典をLLMへ渡す**とする。大量の原文を別サービスへ丸ごと移して、通信と判定費用を増やす構成は採らない。

現在の圧縮は結果本文を省略して判定するため、意味的な選別をそのまま代用できない。候補に必要な内容、原文参照、情報保持条件を追加し、入力予算と再取得回数を含めて評価する。結果が対応済みのJSON HTTP要求に含まれる場合に限り、プロキシ内で実施する。

この変更は送信内容の削減であり、ホスト内部の履歴・文脈量表示・自動圧縮まで短くする保証はない。

## ホスト別の実施方針

| ホスト | 初期の位置付け | 必須条件 |
|---|---|---|
| Claude Code | 最初の実運用検証対象 | Messagesの並列結果、強制ツール指定、推論設定、認証・SSE・承認付き運用を確認する |
| Grok Build | Claudeと並行する実運用検証対象 | 実カタログ名を修正し、`tools` 省略時の素通しを識別する。旧比較の文字列判定に頼らず成果を確認する |
| Codex | 基礎修正に含め、経路確認後に測定 | Responsesの履歴対応、実際のHTTP経路、推論設定の対応を確認する。プロキシを通らない経路は最適化対象外と明示する |
| Cursor Agent CLI | 接続確認と最適化確認を分ける | 既存の無変更記録を成功扱いにしない。JSONとして変換可能な実経路が確認できるまで効果をうたわない |
| Devin CLI | 検証待ち | 設定実装だけで対応済みとせず、実要求・応答と完了品質を確認する |

未対応形式では元の要求を保ち、対応範囲を明示する。CursorのRPC対応などを、この改善のために推測で大きく実装しない。

## 後段へ分ける施策

エージェント全体の改善としては有望だが、今回のプロキシ改善と同時には実装しない。

| 施策 | 後段へ分ける理由・再開条件 |
|---|---|
| 待機・再試行のLLMターン省略 | ホストが要求を出す前の制御が必要。Claude/Grokそれぞれで完了イベント、承認、期限、キャンセルの契約を確認してから実施 |
| 委譲の起動・完了集約 | ツール名の選択だけでは子の状態を管理できない。既存のホスト機構を確認し、定型集計専用のLLMだけをコードへ移す |
| 指示・スキルの選別 | 必須指示と任意資料を区別する構造が必要。原文を文字列処理で一律削除しない |
| 記憶・教訓の整理 | 現行リポジトリの実装範囲外。既存の記録先がある場合に接続し、新しい記憶基盤を作らない |
| モデル選択 | フィールドの変更自体は可能だが、認証・応答形式・品質への影響がある。現在の処理の正確性と採算を確認してから検討 |

定型状態・終了コード・保存処理は通常のコードを優先する。Jevは候補選別や曖昧な結果分類に使い、実装生成、未知の問題の推論、重要な設計判断、最終説明はLLMに残す。

## 実施順序と完了条件

1. **互換性・情報保持を修正** → 検証: 隔離環境で再現した問題を回帰テストで防ぎ、既存テストも成功する。
2. **計測と外部の完了判定を整備** → 検証: 通過・適用・Jev呼出し・タスク成否が独立して判定できる。費用・使用量の欠測が見える。
3. **圧縮・候補数・推論設定を個別比較** → 検証: 同一課題・同一開始状態で実行順を交替し、複数回測定する。キャッシュ条件も記録する。
4. **不要な処理を省き、候補選別を限定導入** → 検証: 検索反復、検索→読取→編集→テスト、並列呼出し、目的変更の各課題で改善を確認する。
5. **ホスト別に採用を決定** → 検証: 完了品質を維持し、タスク全体のLLM使用量と実行時間が改善する。片方だけ改善する案は、そのトレードオフを明示して別判断にする。

中央値だけでなく遅い側の挙動、再試行・再取得、承認付き運用も確認する。タイムアウトや順序保証への影響は、実際の期限・状態遷移に対して検証する。遅いという印象だけで障害原因を断定しない。

削減率・速度向上率の確定値は現時点では提示しない。まず①と②を最初の実装単位とし、その結果を使って③以降の採用を決める。
