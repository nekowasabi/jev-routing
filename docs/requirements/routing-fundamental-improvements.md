# jev-routing の根本的な改善案

## 結論

最優先は、分類器の採用閾値を緩めることではなく、「必要な能力を残したまま、タスク完了までの総費用を減らす」ことへ目的を置き直すことである。そのために、原本の転送、判断用情報の抽出、候補集合の決定、履歴圧縮の成立条件を分ける。

これは IMPROVE.md をもとにした設計提案であり、実装・稼働ログ・外部仕様を今回独立に検証した結果ではない。文書内の実測値を改善効果の予測値として扱わない。

## 先に削る前提

elon スキルの「工程の必要性を確認してから簡素化する」方針を適用する。

| 分類 | 扱い | 理由 |
|---|---|---|
| 明示された目的：コードがツール候補の絞り込みを制御する | 維持 | IMPROVE.md の目標 |
| 不確実による通過を減らすほど良い | 成功基準から外す | 誤った絞り込みでも適用率は上がる |
| すべての要求で分類器を呼ぶ | 必須条件にしない | 削減可能な費用が小さい要求では判断費用が上回り得る |
| 未知形式は要求全体の最適化を禁止する | 変換ごとの成立条件へ変更 | 不透明な原本の保持と、既知部分の操作は別問題 |
| 画像・暗号化情報は判断に不要 | 採用しない | 分類器に読めないことは、意味的に不要なことを保証しない |
| 元の権限・明示的なツール指定・履歴の参照関係 | 維持 | 破ると要求の意味や上流との契約が変わる |

## 1. 適用率から、成功を保った総費用へ — 推奨度 ⭐⭐⭐⭐⭐

IMPROVE.md:34–40 は採用条件と候補数を改善し、78行は適用率を示している。しかし、必要なツールの誤除外やタスクの完了は測っていない。通過は正常な判断結果として残す。

評価するのは、タスク成功率、必要な能力の誤除外、完了までのモデル・分類器・再試行の総費用、完了時間である。キャッシュがある場合は、ツール一覧の変化によるキャッシュへの影響も含める。単なるツール数の削減を費用削減と同一視しない。

まず原要求を変更せず候補集合だけ計算し、実際の次のツール呼び出しを候補内に残せたか比較する。ただし既存モデルの選択が正解とは限らず、候補内に残せてもタスク成功は保証されない。副作用のない評価課題で、絞り込みあり・なしの完了結果まで比較する。

採用条件は「削減見込みが分類と復旧の費用を上回り、品質の許容条件も満たす」。閾値の具体値は評価結果から決める。候補数が少なく効果が出ない要求では、分類器を呼ばず通過させることも改善になる。

## 2. 原本と判断用情報を分ける — 推奨度 ⭐⭐⭐⭐⭐

IMPROVE.md:84、88、116–120 は、入力形式の受理、判断からの除外、圧縮時の保持を近接した問題として扱っている。ここを独立させる。

```text
受信した原本 ───────────────────→ 転送の基礎
      └→ 読める情報＋欠落情報の印 → 候補集合の提案
                                  ↓
                     変更条件を確認して原本へ適用
```

判断用情報には、利用者の直近の要求、参照できる関連履歴、直近のツール結果、実際に利用可能な候補、明示された制約を含める。読めない項目は「存在しなかった」ことにせず、情報が欠けていると表現する。

例えば「この画像のエラーを直して」では画像が選択の根拠になる。画像を原本に保持していても、分類器が画像を見ずに編集・調査ツールを削れば品質は壊れる。このような要求は元の候補を保持する。未知形式も同様に、保存できることだけを根拠に絞り込まない。

新しい大規模な中間言語や共通基盤は不要。既存処理の責務と入出力を分け、判断用情報に欠落状態を持たせるところから始める。

## 3. 「次の一個」を当てる設計から、必要な候補を残す設計へ — 推奨度 ⭐⭐⭐⭐⭐

根拠は IMPROVE.md:25–36。`needs_tool`、単一候補の確信度、複数候補の採用が重なっており、分類結果の評価目的が混在している。

最初の実装ではツール全削除を最適化対象から外し、元の応答・ツール選択の設定を維持したまま候補の部分集合だけを提案する。これにより「応答で終えるか」と「利用可能な能力をどこまで残すか」を分離できる。明示的に指定されたツールや、保持が必要な提供側の定義は削除対象にしない。関係が不明なら当該変更を見送る。

候補集合の採用判定は一箇所に集約する。分類器は候補の点数を返し、コードが保持条件、評価済みの誤除外基準、削減の見込みを確認する。単一候補も複数候補も同じ規則で扱い、被覆条件を満たせなければ全候補を残す。

`p_top / (1 − p_respond)` は条件付きの相対的な集中度であり、安全性の保証ではない。元の点数が校正されていなければ、この計算でも校正はされない。分母がゼロに近い場合や不正な分布を採用しないことも必要になる。

また、単一の「次のツール」の分布を被覆しても、同じ応答で必要な複数ツールを全部残す保証にはならない。並列呼び出しを含む評価を用意する。候補上限に達したら不足分を切り捨てる設計にはしない。

## 4. 履歴圧縮を独立した変換として制限する — 推奨度 ⭐⭐⭐⭐⭐

IMPROVE.md:104 は上流受理を未確認とし、116–120行は不透明ブロックの保持から安全性を結論している。この二つは同じ証明ではない。周辺の履歴を削ると、保存したブロックの依存先や呼び出しと結果の関係が変わる可能性がある。

過去の分析 docs/requirements/test-x-cell-failure-analysis.md:61–71 でも、未知項目を無条件に削除せず、実行主体と保持条件を確認するよう提案されている。形式の既知リストを増やすたびに、要求全体の安全性を暗黙に許可する構造は避ける。

履歴はそのままでツール候補だけ変更できる経路を先に確立する。圧縮は、対応済み形式について呼び出しと結果の参照、順序、上流受理を検証できる場合だけ許可する。未知の依存関係を含む履歴は圧縮しない。

## 5. ログ追加を、判断を再現できる記録へ変える — 推奨度 ⭐⭐⭐⭐⭐

IMPROVE.md:40、94 の上位候補だけの記録では、任意の累積候補集合を後から再計算できない。評価用の記録には全候補の点数、候補一覧の識別情報、保持必須の候補、入力欠落の有無、規則の版、採用・通過理由、実際の呼び出しと結果を対応付ける。

画面と run.log は同じ構造化イベントから作る。通常運用で生の会話や画像を常時保存する必要はない。閾値の再評価は点数と判断入力の構造情報で行い、分類そのものの再現に必要な入力例は、機密情報を除いた評価資料として別に管理する。

接続状態も「鍵未設定」「設定上の無効化」「呼び出し失敗」「分類の棄権」を分ける。IMPROVE.md:110–114 が示す鍵未設定説は有力な仮説であり、原因確定ではない。明示的に Jev 必須として起動する構成では設定不足を起動時に検出し、任意利用の構成では縮退状態を明示する。鍵の値は記録しない。

## 推奨する着手順と検証

1. [成功条件と判断記録を整える] → 検証：保存した点数・候補・規則から採用結果を再計算でき、設定不足と通信失敗を区別できる。
2. [原本保持と判断用情報を分ける] → 検証：画像・暗号化項目・未知項目を含む要求で、変更対象外の値と順序を保持し、情報不足時には候補を削らない。
3. [候補集合の採用規則を一元化する] → 検証：明示的な指定、複数呼び出し、候補の同点、被覆不足、不正な点数で必要な能力を失わない。
4. [副作用のない課題で比較する] → 検証：元の要求と比べた成功率・総費用・完了時間から導入範囲を決める。分類器の計算だけの比較で本番適用の安全性を断定しない。
5. [圧縮や説明文の調整を個別に導入する] → 検証：上流受理とタスク品質をそれぞれ確認する。悪化した変換だけを停止できるようにする。
