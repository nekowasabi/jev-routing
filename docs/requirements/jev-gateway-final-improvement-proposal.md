# ダッシュボード移植とツール選択効率の最終改善案

## 採用方針

**jev-routing のローカル判定と候補限定を活かし、jev-gateway から「信頼できる選択の反映」「引数生成の分離」「使用量の観測」「ダッシュボード」を段階的に取り込む。**

狙いは、依頼の完了品質を維持しながら、高コストLLMが選択・引数生成に使う総費用を減らすこと。ダッシュボードは、その効果と失敗を見えるようにするために移植する。

| 区分 | 最終提案 | 理由 |
|---|---|---|
| 実装を推奨・⭐⭐⭐⭐⭐ | 履歴・ツール対応の修正、Jev回答検証、実通信・上流使用量の計測、読み取り専用ダッシュボード | 誤った状態での選択を防ぎ、効率を測れるようにする |
| 比較実験として推奨・⭐⭐⭐⭐ | 適合ホストへの強制選択、対象ツールを限定した安価な引数生成モデル | 高価なモデルの仕事を減らす候補。実費用と品質で採否を決める |
| 後段の限定検証・⭐⭐⭐ | 全引数を検証できるツールだけLLM呼び出しを省略する `direct` | 構造上の削減効果は明確だが、適用率・スキーマ・承認・継続履歴の条件がある |
| 採用しない・⭐ | gateway全体の置換、毎回Jevへ問い合わせる方式、全ツールへの引数質問追加 | 現行のローカル処理と入力削減を失い、問い合わせを増やすおそれがある |

本書は改善提案であり、製品コードの実装完了や性能改善を示すものではない。

## 1. 選択ロジックは段階構成にする

```text
受信要求
  ↓
形式・履歴・明示されたツール指定を確認
  ├─ 判断材料不足／対象外 → 介入せず既存モデルへ
  ↓
ローカルで選択可能か判定
  ├─ 対象条件で妥当性を確認済み → 候補選択
  └─ 不確実 → Jevへ「次のツール」「今ツールが必要か」を同梱質問
                    ├─ 不正回答／低確信度／矛盾 → 既存モデルへ
                    └─ 妥当な選択 → 候補選択
  ↓
ホストの契約に適合する方法で選択を反映
  ├─ 基準方式：候補限定＋既存モデル
  ├─ 比較方式：強制選択＋既存モデル
  ├─ 比較方式：強制選択＋評価対象の引数生成モデル
  └─ 後段検証：全引数を検証できる場合だけ呼び出し応答を合成
  ↓
クライアントが承認・実ツール実行 → 次の要求
```

「既存モデルへ戻す」は、元要求を上書きせず使えるよう保持して実現する。圧縮済み・推論設定変更済みの要求を、無変更の素通しと呼ばない。圧縮は独立した機能として有効・無効を区別する。

### 選択前に修正するもの

- 呼び出しIDでツールと結果を対応付ける。並列・順不同・未知IDで直前の行動に本文を誤配しない。
- Responses の呼び出し履歴、`additional_tools`、custom形式、名前空間を認識する。認識できることと強制できることを分ける。
- 明示された `tool_choice` を尊重する。サーバー側だけにある履歴や非対応形式では介入を控える。
- Jev回答の型、カタログ内の存在、実確信度、補助質問との整合を検査する。固定確信度を回答の信頼性として使わない。
- 入力予算と目的変更時の圧縮キャッシュを修正し、選択へ渡す状態を正しく保つ。

ローカル処理は残すが、現行の採点値を校正済みの成功確率として扱わない。誤選択が再現するルールは修正・対象縮小し、未検証の採点だけで強制実行を選ばない。

未知・低確信度では候補限定も解除する。Jev失敗時に低確信度のローカル候補を採用して限定する現行経路は修正対象とし、元のツール指定・カタログをモデルへ渡す。

「今ツールが不要」は「依頼が完了した」とは異なる。確認質問や途中説明も前者になり得るため、Jevの要否判定をタスク完了判定に流用しない。

### 高価なLLMの仕事を減らす方法

**最初はモデルを変えず、強制選択の正しさを検証する。** gateway の `forced` はツール名を固定するが、同じLLM呼び出し・全履歴・全カタログが残る。そのまま移しても費用削減を保証しない。現行の候補限定と比べ、推論使用量とキャッシュの変化を測る。

**次に、適したツールだけ引数生成モデルを分離する。** パス・検索式・コマンド・差分・依頼文は自由記述であり、ツール名が決まっても理解や推論が必要な場合がある。ツール種類ごとに検証し、複雑なコード差分やコマンドまで一律に安価なモデルへ変更しない。具体的なモデルは未選定とし、利用可能性・ホストの契約・引数品質を確認して選ぶ。

強制指定に対応しない経路は、候補限定の基準方式または介入なしを使う。Anthropicの思考・キャッシュを保つ末尾ヒントは別の比較候補だが、最終選択をLLMに残すため、選択処理を省略したものとして集計しない。

強制選択の実験対象は、必要な履歴が見え、既決の指定がなく、対応プロトコルで強制できるツールに限る。名前空間付きツール、提供元が実行するツール、`previous_response_id` に依存する見えない履歴、思考設定との非互換は除外する。引数生成モデルの対象は副作用・検証可能性・回復可能性でも絞り、構文が正しいだけで品質合格としない。

**`direct` は既定で無効にし、独立して検証する。** 対応スキーマを限定し、引数なし・定数だけなど検証容易な実ツールから始める。gatewayで再現した複合スキーマの必須引数見落としと、無効設定でも直接生成になる問題を引き継がない。呼び出しID、JSON/SSE応答、クライアント承認、継続要求との整合も合格条件とする。

gatewayには「閉じた引数だけJevで確定し、残りだけLLMへ渡す」部分適用はない。これを初期案へ追加して独自の複雑さを増やす必要はない。

## 2. ダッシュボードは計測と一緒に移植する

### 最小構成

gateway の単体HTML/CSSを参考に、Goの `embed` と既存HTTPサーバーで配信する。まず現在のプロセスだけを表示し、同一オリジン・ループバックの読み取り専用画面とする。Node、Hono、データベース、画面構築用の追加基盤は導入しない。移植したコードには元のMIT著作権表示・許諾文を保持する。

| API・画面 | 内容 |
|---|---|
| `GET /dashboard` | 状態、判定理由、使用量、遅延、直近の要求一覧 |
| `GET /dashboard/events?since=<seq>` | 連番・起動識別子付きの上限付き履歴をJSONで返す |
| 取得方式 | 定期ポーリング。画面のためのSSE接続は追加しない |
| 状態表示 | ローカル選択／Jev選択／介入なし／強制選択／ヒント／直接生成を区別 |
| 変更内容 | 候補限定・圧縮・推論設定変更を独立表示する |
| 履歴範囲 | 保持範囲と欠落を表示し、全期間記録と誤認させない |

初期段階で複数プロセスの自動探索や操作ボタンは必要ない。比較切替えは起動設定から始める。画面操作を追加する場合に、アクセス制御と変更対象の意味を定義する。

### 必須の計測項目

| 計測 | 観測する場所・注意点 |
|---|---|
| 判定元、選択ツール、実確信度、介入しない理由 | 実際の判定結果。`Done` や `Engine=live` を代用しない |
| Jev実呼出し回数、使用量、待ち時間、失敗 | 実通信箇所。圧縮・候補抽出・選択を区別する |
| 上流モデル、状態コード、終了理由、所要時間 | 要求ごとに開始から応答終了まで記録。途中切断も区別する |
| LLM入力・出力・キャッシュ・推論使用量 | JSON/SSE応答から正規化。内数を二重加算しない |
| 再送、モデルへの復帰、追加ターン | 失敗の回復に使った費用も含める |
| タスク完了・総所要時間・総使用量 | 比較実行側の課題IDと外部の完了判定を結合する |

ダッシュボード単体やHTTPプロキシだけでは、タスク完了や全子エージェントの通信を把握できるとは限らない。親子の経路を収集できない場合は観測範囲を明記し、「タスク総費用」と表示しない。

応答は逐次転送しながら観測する。画面計測のために全ストリームを読み終えるまでクライアントへ返さない構成は採らない。部分的な行、JSON、途中切断、二重記録、バッファー上限を検証する。

取得不能値はゼロと分ける。文字数削減をトークン削減と呼ばず、検証していない固定単価から料金を表示しない。初期は実測使用量を表示し、料金を加える場合も計算根拠・対象・欠測を示す。

プロンプト、結果本文、引数、認証情報は画面用履歴へ保存しない。表示項目を許可リストで構築し、上流URLから秘密情報を除く。永続保存・外部待受が必要になった段階で保持期限とアクセス制御を追加する。

## 3. 実装順序と合格条件

| 段階 | 実施内容 | 検証・合格条件 |
|---|---|---|
| 1 | 履歴、ツール対応、Jev回答、入力予算・キャッシュの修正 | 既存の診断失敗を回帰テストにし、並列・Responses・未知ID・目的変更を正しく扱う |
| 2 | 実通信・上流使用量の収集＋読み取り専用画面 | 模擬JSON/SSEの値と画面集計が一致。欠測・切断・再起動・保持上限・秘密値除外を確認 |
| 3 | 適合ホストへ強制選択を追加し、既存モデルで比較 | 明示指定や承認を壊さず、タスク品質を保つ。推論・キャッシュ・追加ターンの実測差を提示 |
| 4 | 対象限定の引数生成モデル分離 | 引数の妥当性と完了品質を保ち、Jev・再試行を含む総費用が基準より改善する |
| 5 | 限定した `direct` の試験 | 完全な入力検証、応答・承認・継続の整合、無効化の保証。実際に省いたLLM要求と回復費用を確認 |

最初の実装単位は段階1と2。これによって、その後の選択方式を評価できる状態を作る。効率改善を優先するため、ダッシュボードの複数プロセス表示・永続ログ・操作機能より段階3と4を先に進める。

## 4. 採否を決める比較条件

修正前の現行実装を記録した上で、段階1の修正後を効率比較の基準にする。既知の履歴誤りによる差を、選択方式の効果に混ぜない。

同じ課題・開始状態・ホスト・モデル条件で、次を分けて比較する。

1. 修正後のローカル／Jev選択＋候補限定。
2. 同一モデルで強制選択を追加。
3. 2の引数生成モデルだけ変更。
4. 適用可能な課題で `direct` の有無を比較。

圧縮と推論設定は比較中に揃える。カタログ限定とキャッシュ保持の比較は別条件にする。単一の最速例を選ばず、実行順を入れ替えて反復し、失敗例・遅い例も残す。

採用条件は **同等の完了品質を保ち、Jev・LLM・再試行・修復を含めた総費用が改善すること**。時間も改善したと主張する場合は総所要時間も確認する。費用だけ改善して時間が増える場合は、その差を明示して判断する。

集計から失敗・中断・低確信度の通過を除外しない。高価なモデルへの復帰費用も含め、ダッシュボード上で実測値と推定値を区別する。

待ち時間の懸念は、タイムアウト総期限、再試行、切断後の残存要求など、破られる具体的な前提へ分解する。単にJevの設定タイムアウトが短いことを高速化の証拠にはしない。

## 5. 変更箇所と今回含めないもの

| 対象 | 主な責務 |
|---|---|
| `internal/proxy/rewrite.go` | 履歴・形式の読解、介入条件、候補限定と強制選択の分離 |
| `internal/plan` | ローカル選択の適用条件、ツール名・結果対応に基づく工程選択 |
| `internal/jev` | 回答検証、実確信度、通信計測、入力予算・キャッシュ |
| `internal/proxy` のHTTP処理と画面資産 | 使用量取得、履歴、ダッシュボードAPI・配信 |
| `cmd/jev-routing` と既存比較処理 | 比較条件の指定と識別、課題単位の測定 |

新しい実行エンジンや独立サービスは作らない。実ツールの実行・承認はホストに残す。大量カタログの多段選択、上流拒否時の自動再送、全引数への先行質問、複数プロセス探索は、必要性と効果が確認できたものだけ後段で追加する。

## 根拠と未確認事項

根拠は、同じコミットを対象とした次の二資料に集約している。

- [移植・互換性・ダッシュボードの分析](jev-gateway-integration-analysis.md): ソース箇所、ライセンス、既存テスト、履歴等の問題再現。
- [ツール選択ロジックの効率性分析](jev-tool-selection-efficiency-analysis.md): `forced` でも上流要求・全カタログ・推論設定が残る模擬検証、`direct` の省略経路と不具合、損益条件。

実サービスでの削減率、Jevの選択精度、安価なモデルの引数品質、実カタログにおける `direct` 適用率は未確認。これらは実装後の比較評価で決める。
