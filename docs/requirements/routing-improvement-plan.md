> 2026-09-23 更新: agmsg 1.4.0 の jev 対応により、ateam の model/effort 自動選択（auto）と `jev-routing route --json` を撤去した。本書の該当記述は履歴として残す。

統合元: `IMPROVE.md`（実測に基づく11案）、`docs/requirements/routing-fundamental-improvements.md`（目的の置き直しと5原則）

## 1. 目的

「LLM は候補の点数付けだけを行い、候補集合の決定・保持条件・閾値判断は code が行うプロキシ」を、**必要な能力を残したままタスク完了までの総費用を減らす**目的で実現する。

成功基準は次の4つ。ツール絞り込みの適用率は成功基準にしない。

| 指標 | 内容 |
|---|---|
| タスク成功率 | 絞り込みあり／なしで副作用のない評価課題を完了できた割合 |
| 誤除外率 | 実際に呼ばれたツール（並列呼び出し含む）が候補集合から漏れた割合 |
| 総費用 | モデル入力トークン＋分類器呼び出し＋再試行の合計。キャッシュ影響を含む |
| 完了時間 | 要求受信からタスク完了まで |

## 2. 先に削る前提

| 前提 | 扱い |
|---|---|
| 不確実による通過は減らすほど良い | 成功基準から外す。通過は正常な判断結果 |
| すべての要求で分類器を呼ぶ | 必須にしない。候補数が少なく削減見込みが判断費用を下回る要求は呼ばずに通過 |
| 未知形式があれば要求全体を最適化対象外にする | 変換ごとの成立条件に変える。不透明ブロックの保持と既知部分の操作は別問題 |
| 分類器に読めない項目（画像・暗号化）は判断に不要 | 採用しない。読めないことは意味的に不要なことを保証しない。欠落として扱う |
| needs_tool の灰色域で choice を棄却する | 廃止。needs_tool は「全ツール削除」判定にのみ使い、初期実装では全削除自体を対象外にする |
| 元の権限・明示的なツール指定・履歴の参照関係 | 維持。破ると要求の意味と上流契約が変わる |

## 3. フェーズ構成

着手順は固定。各フェーズは前フェーズの検証を通過してから開始する。

### Phase 0: 判断を再現できる記録（IMPROVE 案7・10・11 を統合）

**目的**: 以降の閾値と採用規則を実データで決められるようにする。ダッシュボードを開いていない時間帯も解析可能にする。

**実施**
- 1判断=1構造化イベントを定義し、`/dashboard/events` と `run.log`（`FormatStats`）を同一イベントから生成する。
- イベントに含める項目: 全候補の点数（上位3件ではなく全件）、候補一覧の識別情報（名前と件数、host）、保持必須候補（明示指定・sticky）、判断用情報の欠落フラグ、採用規則の版、採用／通過理由、`needs_tool`、API の `confidence`、code 側の集中度 `p_top / (1 − p_respond)`、実際の次のツール呼び出しとの対応。
- 接続状態を4分類で記録: `key_missing` / `disabled_by_config` / `call_failed` / `abstained`。現状の `passthrough:jev_error` は非稼働即通過と API 失敗を区別できない（`rewrite.go:239-259`）ため分割する。
- 起動時に接続状態を1行出力。Jev 必須構成なら鍵未設定を起動時エラーにし、任意構成なら縮退状態を明示する。鍵の値は記録しない。
- 生の会話・画像は常時保存しない。

**変更箇所**: `internal/proxy/rewrite.go`（イベント構築）、`FormatStats`、`internal/jev/jev.go:59` 周辺（`Live()` の状態分類）、`cmd/jev-routing/main.go:146,206`（起動時出力）。

**検証**: 保存したイベントだけから、任意の閾値・被覆率で採用結果を再計算できる。03:20〜04:20 型の空白が起きた場合に原因が1行で残る。

### Phase 1: 原本と判断用情報を分ける（IMPROVE 案8・9・6 を再定義）

**目的**: 受信した原本は転送の基礎として無変更で保持し、判断用情報は「読める情報＋欠落の印」として別に構築する。

```text
受信した原本 ───────────────────→ 転送の基礎（無変更）
      └→ 読める情報＋欠落情報の印 → 候補集合の提案
                                  ↓
                     保持条件を確認して原本へ適用
```

**実施**
- `encrypted_content` と `content` 配列付き `agent_message`（案8）: `messageReason`（`rewrite.go:796-799`）と `contentReason`（`rewrite.go:817-848`）の2箇所で既知の不透明ブロックとして受理する。判断用情報には「不透明ブロックあり」の欠落フラグを立てる。圧縮対象には含めない。`rewrite_test.go:217`（`text` が存在して非文字列なら拒否）は維持する。
- 画像（案9 は不採用）: `reasonImages` を通過理由にはしないが、画像を判断から落として絞り込むこともしない。欠落フラグを立て、Phase 2 の規則で「欠落あり＝候補を削らない」に倒す。画像を根拠に選択できる判断経路ができた時点で再検討する。
- `catalogReason`（案6）: 未知項目1件でカタログ全体を `unrecognized_format` にする挙動（`rewrite.go:556`）をやめる。未知項目は sticky（削除不可）として保持し、名前の取れる候補だけを点数付け対象にする。
- 判断用情報の内容: 利用者の直近の要求、参照できる関連履歴、直近のツール結果、実際に利用可能な候補、明示された制約、欠落フラグ。

**変更箇所**: `rewrite.go:556`、`rewrite.go:793-850`、判断用 state 構築部。新規テスト: `encrypted_content` / `content` 配列 `agent_message` / 画像付き要求 / 未知カタログ項目の各フィクスチャ。

**検証**: 画像・暗号化項目・未知項目を含む要求で、原本の値と順序が保持され、欠落フラグが立ち、候補が削られない。8時間実測で最多の 165 件（Codex `encrypted_content`）が判定対象になる。

### Phase 2: 候補集合の採用規則を一箇所に集約（IMPROVE 案1・2・3 を統合）

**目的**: 「次の一個を当てる」設計から「必要な候補を残す」設計へ変える。分類器は点数を返し、code が保持条件・被覆条件・削減見込みを1つの関数で判定する。

**実施**
- 採用判定関数を1つにする。入力: 全候補の点数、保持必須候補、欠落フラグ、候補数。出力: 保持する候補集合と理由。単一候補も複数候補も同じ規則で扱う。
- 被覆集合: respond を除いて確率降順に累積し、被覆率（初期値 0.9）に達する最小 k を候補にする。上限 ceil(N/2) に達しても被覆率を満たせなければ全候補を残す。切り捨てはしない。
- `needs_tool` は採用判定から外す。初期実装では全ツール削除を対象外にし、応答するかどうかの自由は常に残す。`askNextTool` の灰色域棄却（`rewrite.go:1340-1343`）と `RewriteWith` の再ゲート（`rewrite.go:278`）を削除する。
- `p_top / (1 − p_respond)` は記録用の集中度として Phase 0 のイベントに残す。採用判定には使わない。分母が閾値未満、または点数の合計が不正な分布は「不正」として全候補保持に倒す。
- 保持必須: 明示的に指定されたツール、sticky 項目、提供側定義で保持が必要なもの。関係が不明なら当該変更を見送る。
- 欠落フラグが立っている要求は候補を削らない。
- 費用ゲート: 候補数が少ない（例: Codex の3ツール）など削減見込みが分類費用を下回る要求は分類器を呼ばず通過する。閾値は Phase 3 で決める。

**変更箇所**: `rewrite.go` の `askNextTool` 周辺（`1276-1400`）、`RewriteWith`（`278`）、`topSet`（`1377`）。

**検証**: 明示指定・並列呼び出し・候補の同点・被覆不足・不正な点数の各ケースで必要な能力を失わない。seq5 型（choice 0.93 が needs_tool 灰色域で棄却）と seq6/7/8 型（分布があっても丸ごと通過）が Phase 0 の記録上で消える。

### Phase 3: 副作用のない課題で比較し、閾値と導入範囲を決める

**目的**: 分類器の計算だけで本番適用の安全性を断定しない。

**実施**
- shadow モード: 原要求を変更せず Phase 2 の候補集合だけ計算し、実際の次のツール呼び出し（並列含む）が候補内に残ったかを Phase 0 のイベントで記録する。
- 副作用のない評価課題で、絞り込みあり／なしの完了結果・総費用・完了時間を比較する。
- 被覆率・候補上限・費用ゲートの閾値を評価結果から決める。現行値（0.85 / 0.9 / ceil(N/2)）は暫定。

**検証**: 誤除外率とタスク成功率が許容条件を満たす host・候補数の範囲を特定し、その範囲だけに絞り込みを有効化する。

### Phase 4: 圧縮と説明文の調整を個別に導入する

**目的**: 各変換を独立に有効化・停止できるようにし、悪化した変換だけ止める。

**実施**
- 履歴圧縮: 対応済み形式について、呼び出しと結果の参照・順序・上流受理を検証できる場合だけ許可する。未知の依存関係を含む履歴は圧縮しない。既知リストを増やすたびに要求全体の安全性を暗黙に許可する構造にはしない。
- criteria の対照形式（案4）: 限定導入。Phase 3 で混同する候補ペアが特定でき、実際のツール定義とのずれを検出できる場合に、そのペアだけ `{covers, not_for, examples}` を持つ。未登録は生 description。
- 変換ごとに有効／無効を切り替えられる設定を持ち、Phase 0 のイベントに適用した変換の識別子を残す。

**検証**: 上流受理とタスク品質を変換ごとに確認する。

## 5. 対象外

- model-routes の `no_match`: 全件 `pairs: 0`、`source: legacy`。呼び出し側（ateam）が候補を渡していない問題で、分類器の変更では直らない。
- Grok `passthrough:baseline`: 設定どおり。
- Claude `passthrough:no-catalog`: tools 0。
- 分類器の追加・再接続基盤の新設: 原因が当該機構にあり既存手段で対処できないと確認できるまで不要。
