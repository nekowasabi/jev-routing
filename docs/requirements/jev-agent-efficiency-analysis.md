# AIエージェント全体へのJev適用によるトークン・実行時間削減の分析

調査日: 2026-09-19。対象: `24c7276` と、調査開始時に存在した `internal/proxy/rewrite.go`・`rewrite_test.go` の未コミット変更。以下の「確認済み」はローカル実装・既存記録の確認、「提案」は効果未測定の仮説を示す。製品一般の性能やJevサービスの内部実装を断定するものではない。調査終了時には `scripts/test-x-cell.sh` にも本調査とは別の変更が観測されたため、同スクリプトの指摘・行番号は調査時点の読み取り内容に基づく。

## 結論

**追加改善の余地はある。最も有望なのは、Jevで「必要な情報・次の既定処理」を選び、定型的な実行制御はコードに移して、LLMへ渡す情報量とLLMを介する往復の両方を減らすこと。**

現在の実装は、主にLLMの入力を減らすプロキシである。Jevの判断を追加するだけでは、LLMの呼出し回数は減らず、通信待ちが増えることもある。推奨順序は、既存判定の正確性・計測の整備、不要な処理の省略、検索結果の投入前選別、その後にホスト側の実行ループとの接続である。

削減率・速度向上率は未検証。既存比較は旧コミットのもので、入力本文の縮小が時間短縮や出力トークン削減に直結していない例がある。

### 最初に試す追加用途: 検索結果の投入前選別

例えば検索が多数の候補を返したとき、ファイル版・重複・構文上の条件でコードが候補を絞り、その後でJevが目的に関係する箇所を選ぶ。LLMには選んだ本文、出典、必要時の再取得方法を渡す。

単に結果全体をJevへ移して通信量を増やすのではなく、まずローカルで候補を絞る。エラー、定義と呼出し元、反証となる結果を落とさない保護条件を設ける。少数候補ではJevを呼ばず、選別が不確実なら候補を保持する。現在の圧縮と違い、関連性判定には実際の内容が必要である。

元データが外部サービスや別プロセスの結果である場合、内容をJevへ送ることが既存のデータ取扱範囲に含まれるかも確認する。

### 速度に効く用途: 定型ターンの省略

「実行中か確認→LLMが待機を選択→再確認」の繰返しは、状態と期限が明確ならJevも不要である。ホストが完了イベントを受け取り、結果の要点だけをLLMへ戻せばよい。Jevは終了コードだけでは決まらないログの分類に限定する。

既に生成・承認された処理と引数の実行はコード化できるが、新しい引数の生成や任意コマンドの実行権限まで分類器へ渡さない。再試行は冪等性、上限、順序、キャンセルを保つ。

### 委譲・記録の整理

定型集計だけのエージェントはコードへ移す。Jevは担当選択などの有限選択に使い、独立した推論・調査が必要な委譲は残す。子への入力は対象、制約、完了条件、必要な証拠参照に絞り、全履歴の複製を既定にしない。

提供された判断軸「tel/kb保存専用ncoはフェーズ外フィードバックチャネル」に沿い、保存処理は意思決定の経路から分ける。また「Decideの出力は3宛先に分離」に沿い、実行者には選定案と実行方法、次の観察には観察指示、記録には決定・却下理由を渡す。これらは設計指針であり、本リポジトリでの削減効果は未検証である。

## 拡張前に解消すべき制約

以下は今回見つけた事項で、修正していない。全工程への拡張時に影響するため、優先度を付けて扱う。

1. **会話形式と呼出し・結果の対応。** `input` 配列は取得するが、履歴抽出の `role` 分岐はトップレベルの `function_call` / `function_call_output` を扱わない（`rewrite.go:39–42,273–317`）。結果を最後の未設定アクションに入れる処理もあり、並列呼出しで対応を誤る可能性がある（同`:491–492`）。形式別・呼出しID別の検証を先に行う。
2. **圧縮の判断材料。** Jevに渡す結果は本文ではなく `ok, N chars (omitted)` である（`internal/compact/state.go:23–24`）。重要なエラーや検証結果を内容に基づいて保護できる、とはいえない。
3. **不確実時の保持。** `NoulOf` は欠損・不正回答をゼロとして返し、削除側の値になる（`internal/jev/jev.go:118–130`）。通信失敗と有効な低評価、回答欠損を区別し、不確実なら保持する必要がある。
4. **判断キャッシュの寿命。** 質問IDによるキャッシュはゴール変更を考慮していない（同`:167,236`）。新しいユーザー指示や目的に依存する評価を、内容の再利用と分ける。
5. **確信度の扱い。** 次ツール判定は有効なツール名なら確信度を固定値で扱う（`rewrite.go:179`）。返却確信度を採用しても、そのまま正解率とはみなせない。検証データで校正し、不確実時の保持・候補拡大を比較する。

## Jevを増やさずに改善できる部分

| 施策 | 根拠・狙い |
|---|---|
| 削減余地が小さい要求では圧縮判定を省く | `rewrite.go:61` の履歴件数条件だけでは通信の採算が分からない。追加量・再利用見込み・入力予算を使う |
| 全件キャッシュ済みなら状態整形前に終了する | `jev.go:159,181` ではキャッシュ確認の前に `FitState` を行う |
| 状態を短縮するたびに全体JSONを作り直す処理を減らす | `compact/state.go:62,72,84`。大きな履歴での反復処理を局所的に改善する |
| Jevへ渡す行動履歴を構造化する | `rewrite.go:169` は入力・結果を持つ全 `actions` を送る。対象、試行、終了状態、短い観測、証拠参照へ整理する余地がある |
| ツールを一つに限定する方式と、工程ごとの少数候補を比較する | 一つへの限定はスキーマを減らす一方、複数ツールの一括実行を妨げてターンを増やす可能性がある。カタログの安定性と上流キャッシュへの影響も未検証 |

圧縮と次ツール判定は、圧縮前に構築した行動履歴を参照しているため、現状には並列化できる余地もある。ただし不要な呼出しの省略を先に行い、残った通信の並列化を検討する。リクエストの分割基準にも整合確認の余地があるが、Jev APIの実際の制限を確認せずに変更しない。

## 効果を判断する測定方法

既存の `artifacts/x-cell` には比較記録があるが、調査時のHEADに対する比較はない。例えば `artifacts/x-cell/20260919T131629-96503/claude/comparison.json` には、本文量が減っても時間・出力トークンが増えた比較がある。これは現方式が常に遅いことの証明でもなく、単発の本文削減を速度改善の証拠にできないことを示す。

現行スクリプトの成功判定には `CHECK: PASS` の自己申告を用いる箇所があり、実行順は通常→Jevで固定されている（`scripts/test-x-cell.sh:106,119,134`）。`routing_request_chars` はJSON本文のバイト量で、実入力トークンや請求量ではない（`internal/proxy/proxy.go:149,154`）。

比較条件は「無加工」「ローカル処理のみ」「現行Jev」「新施策を一つ追加」とする。同一開始状態・同一課題で順序を交替し、複数回測る。完了を自己申告だけで判定せず、期待する差分・成果物・受入テストで確認する。

| 評価軸 | 記録するもの |
|---|---|
| LLM利用量 | 実入力・出力・推論の使用量、キャッシュ利用量、親子全体の呼出し回数。取得できない値は欠測と明示し、APIごとの二重計上を避ける |
| Jevの追加負担 | 実際の呼出し回数、クライアント側の待ち時間、失敗・再試行、取得可能な使用量。`latencyMs`だけで通信全体を代用しない |
| 速度 | 完了までの時間、上流応答待ち、ツール実行、Jev待ち、待機処理。中央値と遅い側の分布を見る |
| 品質 | 受入条件の達成、必要証拠の保持、再取得・再試行、ユーザーの修正、誤った候補限定 |
| 適用率 | ホスト・通信形式ごとに、実際に書換えとJev呼出しが行われたかを区別する |

速度の採算は「省けたLLM処理・往復・再読時間」が「追加のJev待ち・ローカル処理・誤判定によるやり直し」を上回るかで決める。これらは並列実行時に単純加算せず、完了までの経路に乗る時間で比較する。

判断軸「壁時計サイクル遅延の影響は何が壊れるか」に沿って、遅延による機能影響は、実在するタイムアウト・期限・再試行上限・順序制御に対して検証する。現行Jev HTTPクライアントには20秒のタイムアウトがある（`internal/jev/jev.go:51`）。これに加えてホストや上流の期限を調べる必要があり、今回それらの違反は実証していない。ユーザーが求める応答速度の改善は、機能破損の有無とは別に測定する。

## 推奨する実施順序

1. **形式対応・情報保持・計測を整える** → 検証: Responses形式、並列呼出し、欠損回答、目的変更で必要情報を失わず、実呼出しと使用量を追える。
2. **不要な判定・重複処理を省く** → 検証: 出力と受入品質を維持し、Jev呼出し・状態整形・待ち時間が減る。
3. **検索結果の投入前選別を小さく試す** → 検証: 必要証拠の保持と完了品質を維持し、総トークン・再取得を含めて改善する。
4. **ホスト側で定型の待機・再試行・集約を実行する** → 検証: LLMターンが減り、期限・順序・冪等性・キャンセルを維持する。
5. **任意資料の選別・委譲先選択へ広げる** → 検証: 必須指示の保持と成果品質を前提に、親子合計で改善する。

最初から汎用ワークフローエンジンを追加する必要はない。ホスト側の既存機構を確認し、繰り返し発生する定型工程だけを接続する。プロキシ単体でできる施策と、ホストへの変更が必要な施策を別々に検証する。
