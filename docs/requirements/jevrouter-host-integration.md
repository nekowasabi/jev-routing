# Jevの判断を各ホストの実動作へ接続する仕様

## 目的と完了条件

利用者の追加要件は、六分類について「判断だけ行って何もしない」状態をなくすことである。**自動捕捉→ローカル／Jev判断→ホストへの適用→実行結果の照合→次の判断**を必須の一続きの処理にする。これは計画上の仕様であり、まだ実装されていない。

`route --json`の追加、候補一覧の絞込み、エージェントへの「利用してください」という推奨だけでは合格にしない。実行が不要という判断、権限待ち、失敗、状態不明もあり得るため、すべての選定を無条件に強行するのではなく、**選定後の到達状態が必ず分かり、未実行を成功扱いしない**ことを保証対象にする。

対象は現行`internal/host/host.go:15`に登録されたClaude・Codex・Grok・Cursor・Devinと、既存ateamの起動経路。各ホストは利用可能な能力だけを扱う。例えばホスト内の子起動機能がなければ、接続済みateam経路を使う。どちらもないのに委譲可能とは登録しない。

## 自動的に呼び出す場所

| 時点 | 自動処理 | 呼出し主体 |
|---|---|---|
| セッション起動 | セッションID・能力一覧・本文参照・実行器対応を準備。必要な接続が有効か確認 | `cmdRun`と`internal/host` |
| 新しいユーザー要求を受信 | 明示指定を保持し、必要なSkills／Pluginsと次の能力を選定 | `Server.ServeHTTP`から共通判断関数 |
| ツール結果・子の結果を受信 | 前回の実行状態を更新し、残件があれば次の能力を選定 | 同じプロキシ入口／ateamの結果受信処理 |
| ツール呼出しをホストへ返す直前 | 選定先・引数・権限・版を照合してホストの実行器へ渡す | プロトコル別の応答処理 |
| 子エージェント起動の直前 | 委譲先とモデル・effortを確定し、実引数へ反映 | ホストの子起動呼出し／ateam |
| 最終応答・切断・終了 | 選定した処理の未配達・未実行・結果未回収を検出して記録・表示 | 応答処理／`cmdRun`終了処理／ateam |

HTTP再試行やストリームの各断片を新しいユーザー要求と誤認しない。要求の内容と処理履歴が変わった単位で判断し、同じ判断を再利用するときも実行状態は再照合する。次の判断は直前の結果を取り込んだ後に行う。

導入時に既存`jev-routing run <host> ...`または設定済みプロキシ経路へ接続すれば、通常の依頼ごとに利用者やLLMが判断CLIを呼ぶ必要はない。ルーターを経由しない起動には適用できないため、到達確認を導入時と受入試験で必須にする。

## 六分類の具体的な適用

| 分類 | Jevが選んだ後に必ず行う接続処理 | 適用・実行の証拠 |
|---|---|---|
| Model | ateam起動前に候補IDを実モデル・effortへ復元し、既存の起動引数へ渡す | 実起動引数。ホストが公開する場合は実際に採用されたモデルも照合し、不一致を成功にしない |
| Subagents | 登録された分担本文を使い、ホストの既存子起動ツールまたはateamへディスパッチ。結果を親の次の要求へ戻す | 起動ID、子の登録、対応する最終結果、親への結果配達。PIDだけでは完了にしない |
| Skills | 信頼済みカタログのIDから本文を読み、要求する追加資料もスキル記述に従って供給。ホスト固有の入力表現で現在の作業コンテキストへ加える | 本文の版・ハッシュと実送信内容の一致。本文配達と、スキルに沿ったタスク成功は別に評価 |
| MCP Tools | 既存接続の正確なツールIDへ解決し、ホストにそのツールの引数を生成させ、呼出しを既存実行器へ渡す | `tool_call_id`／`tool_use_id`等と、対応する結果・エラー |
| CLIs | 登録コマンドの操作を既存シェルツールへ写像し、生成された実行ファイル・引数・作業場所を検証してホストへ渡す | 呼出し内容、実際の終了コード・出力。シェルツール名が一致しただけでは不足 |
| Plugins | プラグインIDを配下の実スキル・MCP・CLI等へ解決し、それぞれの適用処理を呼ぶ | 提供元IDと実行能力IDの対応、本文配達またはツール結果。プラグイン名の選定ログだけでは不足 |

スキル本文は、ユーザーが利用するスキルの内容として出典付きで供給する。既存の上位指示を削除したり、読み取った本文を新しい上位権限に昇格させたりしない。スキルはプログラムではないので「本文を読めばすべて実行済み」とはしない。追加資料のアクセスが認められない場合や入力予算に収まらない場合は明示的な適用失敗にする。

CLIの自由なシェル文字列を名称一致だけで承認しない。登録した操作に安全に対応付けられない構文や別コマンドの混入は適用不一致とする。新しい万能シェル実行器は作らず、ホストの既存承認・実行器を通す。

子への分担内容がまだない場合は、親の通常の引数生成処理で分担内容を確定してから起動する。Jevの役割選択だけで架空のタスクを起動しない。利用者が委譲禁止・固定チームを指定した場合はその制約を維持する。

## JSON系ホストへの接続

共通判断関数はプロキシ内部から呼ぶ。`route --json`は外部消費側のateamと診断で同じ契約を使うための入口である。

- Claude: Anthropicの要求・応答・`tool_use`／`tool_result`の対応を使う。
- Codex: Responsesの要求・応答・`function_call`／対応する結果の対応を使う。
- Grok: Chatの要求・応答・`tool_calls`／対応する結果の対応を使う。

これらの強制ツール選定は既存`internal/proxy/rewrite.go:842`にある。ただしClaudeの思考・キャッシュ指定（`:461`）、Codexの`previous_response_id`付き要求（`:412`）などに既存制限があり、すべての要求が適用可能ではない。工程08で制限ケースを含めて接続を確認する。新設する接続処理では、選定根拠がローカルでもJevでも、適用契約が成立する場合に同じ経路を使う。現状`:331`の`usedJev`依存をそのまま残してローカル確定が候補絞込みだけになることを避ける。

可変引数は既存LLMに生成させる。プロキシは返ってきた名前と引数を検証する。ストリームの場合はその呼出しに必要な断片を完成まで保持し、未検証の呼出しが先にホストで実行されないようにする。中断・不正な呼出しはそのまま実行しない。検証済みの定数引数だけは既存`direct.go`の呼出し応答合成を利用できるが、これは結果の捏造や実行済みの意味ではない。

強制指定は「適切と判断された次の一操作」に限定する。結果受信後に解除・再評価し、応答すべき場面まで同じツールを呼び続けない。複数の呼出しが返った場合はID単位で扱い、未選定の副作用を抱き合わせで通さない。

## Cursor・Devinの独自通信

現在の変換処理は、ツール一覧や履歴を書き戻せても、JSONの強制ツール指定をそのまま転送できるわけではない。

- Cursor: `internal/proxy/connect_cursor.go:1529`の`writeAgentRunRequest`は既存action本文・履歴・ツール一覧を更新する。既存`rewrite.go:465`はこの要求を強制指定不可と扱う。
- Devin: `internal/proxy/connect_devin.go:778`の`writebackDevinHistory`は、新規追加メッセージを既存履歴へ対応付けられなければ失敗する。native経路の既存書戻しだけでは強制ツール指定は届かない。

この二ホストの通信アダプター改修を工程08の必須対象にする。本文供給は、既存のユーザー本文を保持した明示区切りの追記と書戻しで実装する。複数メッセージの構造を推測で新設しない。追加コンテキストのラウンドトリップと実際のモデル向け内容を検証する。

ツール実行は、実際に観測した呼出し・結果のフレーム仕様を固定し、ホストが既に受け付ける呼出し表現へ選定結果を接続する。JSON側に`tool_choice`を追加しただけで対応済みにしない。現時点で、その強制指定・応答変換の実機仕様は未確認である。受入試験はこの未確認を解消する必須条件であり、存在しないフックやフィールド名を仮定して実装しない。

接続方法が成立しない場合、そのホストは`unsupported_application`として自動適用未完了にする。これは対応完了の代替ではない。五ホスト対応の全体完了は、その未完了が解消されるまで宣言できない。従来動作で継続するか適用必須エラーにするかは以下の実行方針で決め、黙って素通ししない。

## 状態・再試行・結果の契約

各判断に`decision_id`を付け、セッション・論理的な要求・候補版・対象操作に関連付ける。LLMにこのIDの生成や記憶を任せない。既存の実行ログ／ateam実行状態を使い、新しい常駐キューやDBは導入しない。

1. `selected`: 候補を決めた。まだ配達・実行していない。
2. `delivered`: 本文または呼出しがホストへ渡った。タスク成功ではない。
3. `started`: 実行開始・子起動等の証拠がある。
4. `result_received`: 対応する結果を受信した。内容が成功とは限らない。
5. `verified`: 事前に定義した受入条件を満たした。

適用不一致・実行エラーは`failed`、既存の承認待ちは`awaiting_approval`、配達したか実行したか確認できない場合は`unknown`とする。スキル配達のように実行開始イベントが存在しない操作では、その状態を捏造せず、種類ごとの必要な証拠で進める。

適用を要求する運用に`application_policy=required`を追加する。未対応経路・ホストが選定を消費しない最終応答・適用前検証失敗は、プロトコルに合う明示エラーと実行状態へ反映する。処理を通常の完了として返さない。既存動作の継続を選ぶ`fallback`では元候補／従来設定へ戻し、復帰理由とJev選定が未適用であることを表示する。`observe`は評価用であり、今回の自動適用の完了には数えない。

新しい自動適用を有効にした場合の既定は`required`とする。`fallback`は明示指定時だけ使い、復帰を自動適用成功に含めない。新規設定を使わない既存起動は従来の動作を維持する。導入例と受入試験は自動適用有効・`required`で実施し、設定なしで動いたことを新機能の証明にしない。

判断の不確実さやJev障害による既存設定への復帰は許容する。一方、採用した判断を届けたふりで終わることは許容しない。実行器に送った後の応答消失は副作用の成否が不明なので、自動的に再送しない。履歴・ホスト状態を照会し、確認できなければ`unknown`を残す。外部ホストとの厳密な一回実行を保証できるとは主張しない。

内部で安全に再試行できるのは、実行器への配達前だと確認できる判断・引数生成処理だけとする。修復は同じ全体期限内で一回まで。再試行で新しい子や同じ副作用を増やさない。キャッシュは判断結果に限定し、過去の実行成功を今回の結果として使わない。

## ateamの起動から結果回収まで

モデル設定を渡すだけでなく、委譲判断を既存の起動処理へ接続する。起動前に`dispatch_id`を実行状態へ記録し、同じ要求の再処理は既存の起動・結果を参照する。名簿の再解決・新しいrun_idだけで別起動にしない。

子からの最初のメッセージをタスク成功とみなさない。開始・進捗・最終結果を区別し、最終結果を依頼した分担IDへ対応付けて親へ戻す。中断後の再開では既読化されたメッセージも永続履歴から回収する。AGMSGの通信方式を変えず、ateam側の相関情報と実行状態を拡張する。既存の通常起動・待機との互換性を維持し、厳密な結果封筒は新しい自動委譲経路へ適用する。

根拠: `A/scripts/ateam.py:683`は毎回run_idを作り、`:943`以降のwaitは起動済みメンバーの返信を待つ。受信済み集合は`:951`のメモリ上にあり、`:925`のcloseは実行状態を削除する。新経路はdispatch_id単位の排他・起動前保存・終端記録保持を加え、既存AGMSGの機械可読履歴を再利用する。一部メンバーの起動に失敗したpartial状態も、必須役割が揃わない限り成功にしない。

子が失敗した場合や返信が不明な場合は親へその状態を渡す。自由文の「完了しました」やプロセス終了コードだけで業務上の成功にしない。機械的な受入条件がある分担はそれを実行し、ないものは結果受信までの証拠と内容検証の未確認を区別する。

## 受入試験

共通の試験は、ホストを起動して通常の依頼を一度渡すだけで、判断CLIの手動実行なしに各分類の実動作を確認する。

| 分類 | 成功例の証拠 | 「判断だけ」を検出する失敗例 |
|---|---|---|
| Skills | 選定本文の供給と、スキル固有の受入条件を満たす成果物 | 本文未配達、スキル未適用のまま通常回答 |
| Plugins | 対象プラグインの実能力が呼ばれ、その結果を確認 | 提供元の選定ログしかない |
| MCP Tools | 呼出しIDに対応するサーバー結果 | 名前だけ絞ったが呼出しがない |
| CLIs | 登録操作の実引数と終了結果 | 別コマンドを呼ぶ、呼ばずに説明で終了 |
| Subagents | 子起動→対応する最終結果→親への配達 | 起動だけ、進捗返信だけ、結果未回収 |
| Model | 選んだモデル・effortが起動引数へ反映 | 判断記録と実引数が違う |

ホスト×利用可能な六分類の対応表を試験結果に残す。未対応経路や権限未付与を分母から黙って除外しない。再送・切断・中断再開・二重応答・承認待ち・Jev停止・選定後の能力削除も試験する。Goの偽上流とPythonの偽spawnで契約を検証した後、各ホストの実環境で無害な試験を実施する。模擬試験だけで実ホスト対応完了とはしない。
