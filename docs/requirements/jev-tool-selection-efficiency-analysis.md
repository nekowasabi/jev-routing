# Jevへのツール選択委譲は、現行より効率的になるか

## 結論

**jev-gateway の選択処理をそのまま移すだけでは、jev-routing より効率的になるとはいえない。現行もすでにツール選択をローカル処理またはJevへ移している。追加価値があるのは、選択結果をどのようにLLM処理の削減へ結び付けるかという部分である。**

有望な移植対象は、確信度と整合性を検査した上での強制選択、引数生成モデルの分離、限定されたツールでのLLM呼び出し省略。ただし、一般的なコーディング用ツールでは自由記述の引数が必要であり、LLMの仕事は大きく残る。まず「選択済みツール＋安価な引数生成」の比較実験を行い、全引数を安全に確定できるツールだけで呼び出し省略を検討するのが妥当である。

ダッシュボードはこの判断を支える計測画面として扱う。画面移植自体をツール選択効率の改善とは数えない。

## 何が同じで、何が違うか

| 比較軸 | jev-routing | jev-gateway | 効率への含意 |
|---|---|---|---|
| 選択の入口 | ローカル工程・名前・説明の採点。確信度が閾値未満ならJev | 除外条件に該当しなければJev | gatewayへの単純置換はJev通信を増やし得る |
| Jevへの問い | 次のツール＋要求が満たされたか | 次のツール＋今ツールが必要か。条件付きで引数も質問 | 選択と補助質問を一つの要求へまとめる仕組みは現行にもある |
| Jevへ渡す状態 | 最新の作業要求と行動履歴 | システム指示と最近の正規化された会話 | gatewayは判断材料を増やすが、入力量も増え得る |
| 選択結果の反映 | カタログを1種類へ限定し、`tool_choice` を削除 | `forced` は `tool_choice` で種類を固定 | 前者は候補削減、後者は出力制約。別の機能である |
| 上流のカタログ | 選択成功時は1種類 | `forced` でも全カタログを保持 | gatewayだけではスキーマの入力削減にならない |
| 上流の推論設定 | 条件に応じて変更 | `forced` は元設定を保持 | 強制選択しただけで推論トークンが減るとは保証できない |
| 上流モデル | 元モデル | 任意の `ARGS_MODEL` に変更可能 | ここが高価なモデルの利用削減につながる明確な追加機構 |
| LLM呼び出し数 | 要求を上流へ転送 | `direct` のみ上流を省略 | 応答合成が成立する要求だけ、LLM呼び出しそのものを消せる |

根拠: `R/internal/proxy/rewrite.go:60,73,75,116,149`、`R/internal/plan/plan.go:189`、`G/src/decide.ts:115`、`G/src/questions.ts:113`、`G/src/adapters/chat.ts:59`、`G/src/adapters/responses.ts:152`。

現行のローカル確信度も、成功確率として校正済みではない。工程一致で固定値を返し、説明文の採点を別途確信度へ変換する（`R/internal/plan/plan.go:218,221,228`）。「ローカルなら常に正確で安い」とは評価せず、正答率と再試行まで含めて残す範囲を決める。

## LLMから取り除ける仕事

### `forced`: ツール名は固定できるが、LLMの難しい仕事が消えるとは限らない

gateway の実装は元要求を展開し、主に `tool_choice` と任意のモデル名を変更する。全履歴・全カタログ・元の推論設定を引き継ぐ。

`Read(path)` のパス、`Grep(pattern)` の検索式、`Bash(command)` のコマンド、`apply_patch` の差分、子エージェントへ渡す依頼文は、自由記述である。どのツールか決まっていても、その引数生成にコード理解や計画が必要な場合がある。「名前選択を外したから小型モデルで同品質」とは結論できない。

したがって、同じ高価なモデルへ `forced` を付けるだけの移植は優先度が低い。**現行の候補限定を活かしつつ、適したツールで強制選択と安価な引数生成を組み合わせる案**が比較対象となる。ただし、これはgatewayにそのまま存在する構成ではなく、両者を組み合わせる提案である。カタログ変更とプロンプトキャッシュの関係も測定する。

### `direct`: LLMを省略できるが、適用範囲は狭い

`G/src/questions.ts:54` は全プロパティが定数・列挙値・真偽値のときだけ引数を確定可能と扱う。ひとつでも自由文字列・通常の数値・複雑な構造があれば、そのツールの引数全体をLLMへ戻す。

**「列挙引数だけJevが埋め、自由記述だけLLMに渡す」という部分委譲は実装されていない。** 選ばれなかったツールの引数に対する先行質問も発生する。問い合わせの一括化は往復を節約し得るが、質問処理や入力の費用が無料になる意味ではない。

全引数が確定すれば `G/src/app.ts:144` で応答を合成し、上流LLMを呼ばない。実ツールを実行するのは従来どおりクライアントであり、ツール実行時間や、その後の結果解釈・最終回答まで消えるわけではない。

前回、`allOf` 内の必須文字列を見落とし、`direct` と空引数を返す挙動を再現した。既存の `direct` を丸ごと移すのではなく、対応スキーマを明確に限定し、対応外ならLLMへ戻す必要がある。無引数・固定選択式の実ツールが実運用でどの程度使われるかは未確認。

### `hint` と `none`: 費用削減とは切り分ける

`hint` はツール名の提案を会話末尾に足し、最終判断をLLMへ残す。推論有効・キャッシュ利用を検出したAnthropic経路で使われる。LLM呼び出しや候補を消さないため、主に選択品質の改善候補として評価する（`G/src/adapters/messages.ts:88,108`）。

`none` も回答を生成するLLMは呼ぶ。「今ツール不要」と「依頼を完了した」は同義ではない。確認質問・中間説明でも前者になり得るため、gatewayの `needs_tool` を現行の完了判定 `done` へそのまま割り当てない。

## 問い合わせの一括化は、新規性と費用を分けて評価する

現行の `askNextTool()` も「次のツール」と「完了度」を同じ `c.Ask()` へ渡す。gatewayの新しい点は、これに全引数が閉じた候補の引数質問を先行して同梱することである。選択した後で引数用の要求を送る方式と比べれば往復を省けるが、現行の選択だけの要求より常に安いわけではない。

`G/src/questions.ts:141` は追加引数質問を上限付きでカタログ順に生成する。上限に達した後のツールは直接生成対象から外れるため、順序で適用機会が偏る。大量カタログでは `G/src/decide.ts:126` の候補抽出と最終判定が逐次になり、状態を両要求へ送る。追加質問の費用・時間と、LLM要求を省略できる頻度の釣り合いを測る必要がある。

また、現行はローカル選択でJevを省いても、前段の圧縮判定でJevを呼ぶ場合がある。Jev選択に失敗した場合は元のローカル判定が残り、必ず全カタログ通過になるわけでもない（`R/internal/proxy/rewrite.go:61,76`）。両実装の単純な「1ターンあたり通信回数」の比較では、これらの分岐を落とさないこと。

## 最小の移植案と推奨度

| 案 | 推奨度 | 理由・採用条件 |
|---|---|---|
| Jevの実確信度・回答型・補助質問との整合で介入判定 | ⭐⭐⭐⭐⭐ | 現行の固定確信度を改善し、誤選択による無駄なターンを抑える候補。改善率自体は未測定 |
| 不確実な選択をJevへ送り、適合ホストで選択を固定 | ⭐⭐⭐⭐ | 選択を高価なLLMへ戻さない仕組み。ただし指定済み選択・名前空間・推論設定等の契約を守る |
| 適したツールだけ引数生成モデルを分離 | ⭐⭐⭐⭐ | 同じLLMを呼ぶだけの構成から進める。パス・検索等と、コード差分・複雑なコマンドを別々に評価 |
| 全引数が安全に確定するツールだけ `direct` | ⭐⭐⭐ | 一回のLLM要求を省略できる。利用頻度、スキーマ検証、クライアントの承認・継続処理が成立条件 |
| gatewayのJev常用・全カタログ保持をそのまま採用 | ⭐ | 現行のローカル判定省略・スキーマ削減を失い、通信と入力が増える可能性 |
| 全ツールの引数質問を常時追加 | ⭐ | コーディング用の自由記述ツールでは結果を活用できないことが多い。実カタログの適用率を先に測る |

選択処理の最小案は「安全に確定できるローカル判定 → 残りをJevで選択・整合性確認 → 適合する場合だけ強制選択 → 評価済みの引数生成モデルへ」という段階構成。`direct` は独立して比較する。履歴圧縮の問い合わせは別目的なので、選択を一括化するという理由だけで統合しない。

ダッシュボードには、この分岐ごとの件数と、Jev実呼出し、入力量、上流モデル、使用量、再試行、タスク成否を表示する。既存の `Engine=live` から実通信回数を推定してはいけない。

## 効率改善を証明する比較

比較対象は「通常の高価LLM」だけでなく、**現在のjev-routing**を必ず含める。

1. 現行: ローカル／Jev選択＋候補限定。
2. 同一モデルのまま、確信度検証と強制選択を追加。
3. 2に評価対象の安価な引数生成モデルを追加。
4. 3とは独立に、適用可能な要求だけ `direct` 化。

圧縮・推論設定・入力履歴を揃え、選択方式の差と混ぜない。引数が正しく実行可能で、依頼全体が完了したことを外部テストで判定する。

費用は「Jevの全要求＋LLMの全要求＋失敗後の再試行・修復」をタスク全体で比較する。ある1要求で小型モデルへ変えても、修復が増えれば不利になる。費用と時間は別々に評価し、タイムアウトを評価するときは総期限・再試行・切断後の残存要求という具体的な前提を確認する。

概念上の採用条件は次のとおり。単価や削減率の実測値ではない。

```text
同等の完了品質を維持し、
導入後の（Jev費用＋LLM費用＋修復費用） < 現行の総費用
時間も改善と主張するなら、タスク全体の所要時間も現行より短い
```

閉じた引数の比率、強制選択の受理率、選択精度、小型モデルの引数品質、キャッシュ影響が未測定なので、現時点で費用削減率・高速化率は提示できない。

## 今回の模擬検証

クローン内で `node --import tsx --input-type=module` により、実際の `createApp()` と既存の `fakeJev` / `fakeUpstream` を組み合わせた。自由文字列と真偽値を持つツール、真偽値のみのツールを入力し、3経路を検証した。Jevの選択回答・上流応答は模擬値であり、判断の正答率・性能は測定していない。

```text
node mock comparison exit=0
forced-default: Jev=1 questions=3 upstream=1 model=expensive-model forwardedTools=2
forced-cheap: Jev=1 questions=3 upstream=1 model=cheap-model forwardedTools=2
direct: Jev=1 questions=3 upstream=0 model=none forwardedTools=0
PASS: forced preserves full catalog/history/reasoning; only direct skips upstream
```

アサーションで確認した内容:

- 通常の `forced` は元のモデルを呼び、`ARGS_MODEL` 指定時だけモデルが変わる。
- `forced` は全ツール定義・履歴・`reasoning_effort: high` を維持する。
- `direct` は上流を呼ばない。
- 自由文字列を含むツールの真偽値引数はJevへ部分委譲されない一方、選ばれていない確定可能ツールの引数質問は生成される。

追加で、`directCalls:false` と無引数関数を `decide()` へ渡すと、`direct` が返ることもアサーション付きで再現した。

```text
node direct toggle check exit=0
REPRODUCED: directCalls=false still returns direct for no-argument function
```

`G/src/questions.ts:139` が作成済みの計画を返し、`G/src/decide.ts:183` が設定を再確認しないためである。移植や比較実験では、この無効化設定が完全に機能すると仮定しない。これも期待動作の成功ではなく、問題挙動の再現成功を示す。
