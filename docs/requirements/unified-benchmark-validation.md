# 統合ベンチマークと結果表示の最終改善案

状態：計測・比較記録・ダッシュボード、`direct` 条件、`x-cell` 共通ランナー、Claude Code の同一モデル親子計測を実装。４ホストの実課題を診断した。Grok Build は CLI 集計、Devin CLI は ATIF 手順合計を検証できた単独セッションに限り、要求別の欠測を残したままトークン KPI を比較する。Grok Build／Devin CLI の子使用量は未取得で、その課題は比較不能。反復効果は Claude Code と Codex の各６ペアで判定済み。Grok Build／Devin CLI の反復判定、長い親子セッションは未完了。関連する実測と残課題は [MEMO.md](../MEMO.md)。

## 目的と統合判断

成果の品質を保ったまま、親・子エージェントの上流 LLM と Jev を合わせた**実測総トークン**を減らせたかを判定する。失敗した試行の消費も含め、「成果を一件得るまでに必要なトークン」を併記する。経過時間は副指標とする。候補数、送信バイト、推定削減量は原因分析用とし、主指標を代用しない。

ライブ検証の入口、ホスト起動、反復順、計測、結果形式、比較を `jev-routing bench` に統合する。`x-cell` の読み取り課題と既存 `bench` のチェス課題は、共通ランナーに登録する別課題として残す。課題ごとの準備と外部採点は各課題に持たせる。現行の二重実装は、[x-cell の起動](../../scripts/test-x-cell.sh#L74)と[bench の起動](../../internal/bench/run.go#L259)にある。

二種類の対照条件を維持する。`direct` はホストをプロキシなしで起動し、`passthrough` は同じプロキシ経由で本文を変換しない。前者は導入全体の差、後者は変換単体の差を測る。現行 `x-cell` は前者、`bench` の `off` は後者である。[x-cell](../../scripts/test-x-cell.sh#L90)・[bench](../../internal/bench/gateway.go#L28) **施策の主比較は同じ計測源を持つ `passthrough` 対介入**とする。`direct` はホストの自己申告使用量しか得られない場合があるため、`passthrough` で CLI 側とプロキシ側を併記して計数の差を較正できたときだけ総トークンを比較する。本番の `jev-routing run` 経路はライブ比較に含め、プロキシの直接起動は通信契約の確認に利用する。起動経路を結果へ記録する。

## 実行条件と比較の単位

| 条件 | プロキシ | 選択 | コンパクション | 比較目的 |
|---|---|---|---|---|
| `direct` | なし | なし | ホスト既定 | 導入全体とホスト環境の差 |
| `passthrough` | あり | なし | なし | プロキシ接続自体の差 |
| `selection` | あり | あり | なし | ツール選択だけの効果 |
| `compaction` | あり | なし | あり | 圧縮だけの効果 |
| `combined` | あり | あり | あり | 二機能の相互作用 |

`selection`／`compaction`／`combined` の推論設定、ホスト、モデル、課題、候補カタログ、権限、開始状態をそろえる。`JEV_REASONING=preserve` を明示し、要求別の `reasoningChanged=true` が一件でも出た選択比較は不成立とする。現行 `bench` は既定の `legacy` を継承し、選択適用時に推論を変え得る。[既定値](../../internal/proxy/options.go#L56)・[変更箇所](../../internal/proxy/rewrite.go#L480) スキル本文の自動供給と `forced`／`direct` は、選択の通常経路と混ぜず別条件として記録する。`passthrough` では `JEV_AUTO_APPLY=off` を明示し、本文が変換されないことを確認する。プロキシの `baseline` モードは圧縮も停止するため、圧縮単独条件は変換フラグで表現する。[圧縮の適用条件](../../internal/proxy/native_compact.go#L41)・[選択無効時](../../internal/proxy/rewrite.go#L189)

実 LLM を使う検証では、利用者指定の `gpt-5.6-terra`・推論量 `medium` を基準にする。この組合せを受け付けないホストの結果を同一モデルのペアへ混ぜない。ホスト別の接続可否と実送信モデルは実行前に確認する。固定応答だけの計測契約試験では LLM を呼ばない。

比較単位は「同じホスト・モデル・課題・設定・ソース版の対照／介入ペア」とする。実行順を交替し、キャッシュの条件を記録する。予備計測でばらつきを見てから反復数と採否の閾値を事前に固定する。各課題・ホストのペア差と分布、比較可能数／全件数を表示する。条件ごとに別々に取った中央値の差や、異なる課題の中央値を再集計した値だけで採否を決めない。[現行の群別中央値](../../internal/bench/report.go#L251) 製品全体に一つの削減率を付けるには、対象業務の課題構成と重みを先に固定する。それまではホスト・課題別の判定を正とする。

## 先に通す計測・通信契約

1. ホスト別の上流使用量を正規化する。Claude の総入力は未キャッシュ入力、キャッシュ読取、キャッシュ書込の合計。OpenAI 形式ではキャッシュ読取は入力の内数として扱う。推論は出力の内数なら重ねて足さない。[Anthropic](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)・[OpenAI](https://developers.openai.com/api/docs/guides/prompt-caching) 非キャッシュ入力とキャッシュ書込は総トークンと別に示す。総量が減ってもキャッシュが崩れた場合は「費用・速度に懸念のある削減」として切り分ける。これを採用の禁止条件にするかは、利用者の目的と予備計測を踏まえて決める。
2. Jev の実入力・出力使用量を公式応答形式で取得する。[TypeSafe API](https://docs.typesafe.ai/api) 現行の[受信構造体](../../internal/jev/jev.go#L90)は別のキー名を期待するため、公式形式の固定応答で先に照合する。失敗した HTTP 試行の使用量が不明なら「未計測」とする。
3. 上流推論要求、制御要求、Jev 要求、実ツール呼び出し、ホスト再試行、親・子セッションを区別する。現行の `bench` は全イベントを `Requests` と数える。[実装](../../internal/bench/gateway.go#L201) 子の通信が同じ計測境界を通ったと確認できないランでは、親子合計を宣言しない。
4. 各要求の「候補選定→要求への適用→上流受理→ホストの実ツール実行→結果」を対応付ける。`ObservedTools` は重複を除いた名前だけなので、回数・呼出し ID・並列群を正しく取得できるかを契約確認に含める。[実装](../../internal/proxy/decision_event.go#L250)
5. 計測器の失敗を独立して記録する。上流使用量が必要な**推論応答**の件数に対して、使用量取得件数、途中終了、部分使用量、メーター取得エラーを照合する。制御要求、上流を呼ばない `direct`、ローカル圧縮応答は使用量の期待件数から除く。現行の[メーター失敗](../../internal/bench/run.go#L329)はログ出力後も使用量０のレコードが残り得る。固定の待機時間が過ぎたことを完了証明にしない。[現行の待機](../../internal/bench/gateway.go#L177)
6. イベントの途中欠落を検出する。現在のメモリ上限は直近 1000 件であり、長いランの集計元としてそのまま使わない。[実装](../../internal/proxy/events.go#L10) 計測が不完全な旧形式の結果も、既定では比較不能とする。
7. 外部採点器の失敗と成果の失敗を分離する。現行チェス検証器は作業領域のコードを読み込んだプロセスの標準出力から採点 JSON を読むため、採点行の真正性と件数を検証する。[読取側](../../internal/bench/verify.go#L64)・[実行側](../../internal/bench/assets/chess/verify.mjs#L192) 出力偽装の発生は未確認だが、採点器エラーを品質不合格として集計しない。

計測が欠けたランは総量をゼロ補完せず「計測不完全」とする。成果が失敗したランは捨てず、成功率と失敗に費やしたトークンを表示する。**成功ペアだけの中央値を主効果としない。** 全ての開始済みランの使用量と成果を同時に扱い、成功ペア限定の差は補助指標に置く。

## ランごとの採否と報告

1. **品質**：終了状態と独立した外部成果を確認。採点器自身の失敗を区別する。失敗ランも件数と消費量を残す。
2. **適用**：要求がプロキシに届き、意図した `advise`／`filter`／`forced`／`direct`／圧縮が行われ、上流またはホストに受理されたかを確認。介入がゼロ件のランを「効いた」としない。
3. **計測**：使用量が必要な全推論応答と Jev 試行、親子セッション、イベント、実効設定が揃っているかを確認。不完全なペアは差分を算出せず、欠測件数と条件を表示する。
4. **比較**：主比較は `passthrough` 対 `selection`。全ての開始済み反復ペア（品質失敗を含む）の総トークン比を使い、ペアごとの対数比の中央値と不確実性区間をホスト・課題ごとに出す。成功ペア限定の差は補助表示とする。各条件で**全ランの総トークン÷外部検証に成功した件数**も示し、安く失敗する施策を節約と呼ばない。成功０件では値を定義しない。
5. **採否**：品質の非劣性と、事前に定めた実用上の最小削減幅を両方満たしたときだけ「改善」とする。品質が下がった場合、または総トークンが増えた場合は「悪化」。効果が不明瞭なら「保留」、設定不一致・欠測・採点器失敗なら「判定不能」とする。非キャッシュ入力やキャッシュ書込の悪化は別の注意として表示し、総トークン削減と混同しない。

実用上の最小削減幅、許容できる品質差、反復数、不確実性区間の計算法は**効果を見る前**に登録する。候補としてペア対数比のブートストラップ区間を使うが、少数反復で区間が安定しない場合は採否を保留する。数値閾値を今回の未実施データから作らない。複数のホスト・課題・条件を後から選んで「製品全体で改善」としない。製品全体の表示には対象業務の事前固定した重みと主要比較を必要とする。[現行の課題名だけの群分け](../../internal/bench/report.go#L251) 対照ランがない場合は相対差を出さない。現行[チャート](../../internal/bench/chart.go#L234)は対照なしでも代用値から相対値を作れるため、旧図を効果の証拠にしない。

## ダッシュボードの表示契約

保存済み結果とライブ要求を区別する。比較画面の最上段は**判定、品質、総トークン差、比較可能ペア数／全件数**の四項目とし、判定語彙を「改善／悪化／保留／判定不能」に固定する。品質失敗や計測不完全がある場合は理由を先に表示し、欠測した総量を０として描かない。色だけでなく文言と記号で状態を示す。「推定削減」は実測使用量と同じ棒に載せず別枠にする。[現行の混在表示](../../internal/proxy/assets/dashboard.js#L79)

| 先頭の判定 | 一目で示す理由 | 総トークン欄 |
|---|---|---|
| 改善 ↓ | 品質の条件を満たし、事前登録した最小削減幅を不確実性区間まで満たす | 対照・介入の実測値、ペア差と区間 |
| 悪化 ↑ | 品質の非劣性に失敗、または総トークンの増加が確か | 対照・介入の実測値、悪化した課題 |
| 保留 ? | 効果が不明瞭、反復不足、またはキャッシュ等との未決の取引条件がある | 実測値と不足している判断条件 |
| 判定不能 — | 設定不一致、計測欠落、採点器の失敗などで比較が成立しない | 数値の代わりに欠測理由 |

次段は**ホスト×課題の一覧**とし、各セルに品質状態、総トークンのペア差、計測完全性を示す。悪化または判定不能のセルを先に見られるようにし、全ホストの異なる意味の `inputTokens` を合算しない。セルから、上流入力（非キャッシュ／読取／書込）、上流出力、Jev 入出力、上流推論／制御／Jev 要求、実ツール回数、再試行、子セッション、時間へ掘り下げる。最下段に要求単位の「選定→適用→実行→結果」の時系列を置く。比較元のないライブ表示は「比較なし」とする。現在の[比較欄](../../internal/proxy/assets/dashboard.js#L796)は JSON の整形表示に留まるため、保存済み結果から再計算した同じ指標を読み込む表示へ移す。

## GitHub に残す記録

各ランを `benchmarks/records/<run-id>.json` のような**版付きの一ファイル**に保存する案とする。観測データの正本はこのファイル、指標計算の正本は集計コードとし、表・図は再生成する。内容は許可リスト式に限定する。プロバイダ原形式の**使用量数値欄だけ**と正規化値・正規化器の版を併記し、将来の計算誤りを生データに戻らず訂正できるようにする。

| 含める | 含めない |
|---|---|
| スキーマ版、ソースコミットと未コミット差分の有無、ラン・ペア ID、課題と採点器の版、ホスト／CLI／実送信モデルとその版、起動経路、比較に影響する非秘密の実効設定（mode、compaction、reasoning、selection、transforms、cost gate、種類別モードなど）、実行順とキャッシュ条件、品質と採点器の状態、許可した使用量数値欄と正規化値・正規化器の版、欠測理由、親子の識別、適用方式、実ツール回数と結果状態 | 認証情報、生の要求本文・ツール引数・CLI 出力、スキル本文、絶対パス、作業ツリー、未検査のイベント JSON |

現行の `results/` と `artifacts/` は Git 管理対象外であり、生ログを含む。[gitignore](../../.gitignore)・[bench の保存](../../internal/bench/run.go#L200)・[x-cell の保存](../../scripts/test-x-cell.sh#L35) 生ログは従来の非追跡領域に保ち、将来 GitHub へ残す場合も許可項目だけを書き出す。別環境ではリポジトリを取得し、同じ集計コードから報告・ダッシュボード表示を再生成する。保存済み記録をブラウザから読み込む方法なら、既存のライブ表示を大きく変えずに確認できる。**全作業が終わるまで GitHub には公開しない。** 旧 `runs.jsonl` と旧 `comparison.json` は上記の使用量・条件を欠く場合、既定で主指標の比較不能と表示する。

書き出しの合格条件は、許可キー以外が出ないこと、秘密を模した識別文字列と絶対パスが残らないこと、別環境で同じ版の集計コードから同じ品質・使用量・判定を再生成できることとする。Git に残す記録だけで原因を追えない場合は、ローカルの生ログと記録のラン ID で照合する。生ログの保存期間と公開範囲は記録とは別に扱う。

## 実測前に確定する値

| 項目 | 決め方 | 未決のまま実行した場合 |
|---|---|---|
| 実用上の最小トークン削減幅 | 予備計測のばらつきと利用者が求める効果から、主要比較ごとに事前登録する | 小さな偶然差を「改善」と呼べない |
| 許容できる品質差と反復数 | 課題群の失敗率を予備計測し、比較開始前に固定する。固定通信契約は全件合格を要する | 品質非劣性と不確実性を判定できない |
| キャッシュ悪化の扱い | 総トークンとは別の費用・速度上の制約として、許容する変化を事前に決める | トークン削減とキャッシュ回帰が併存したランは「保留」とする |
| 製品全体の課題重み | 実際に対象とする業務の構成を先に固定する | ホスト・課題別の結果だけを提示する |

## 実装に進む場合の移行順

計測と結果形式を先に一本化し、固定応答で数値の正規化・欠測・推論設定維持・呼出し数を確認する。既存の `x-cell` と `bench` の課題・採点器を順に接続し、二つの入口は移行中に薄い互換口として同じ保存形式と集計を使わせる。共通のランで品質・適用・計測が成立してからダッシュボードの比較表示と Git 管理用の書き出しを接続する。保存済みの旧結果は形式版を分け、欠測項目を推定で埋めない。

## 現行実装との対応と未充足条件

実装した効果判定は `--min-pairs 6`、`--min-savings-pct 0` を事前条件とし、総トークンのペア削減率中央値に対する正確な順序統計の95%以上の区間を使う。比較不能ペアが一つでもあれば効果は判定不能、品質悪化は優先して失敗とする。単発ペアの削減値は診断値であり「改善」の表示には使わない。`comparison.json` とダッシュボードに比較可能件数、品質、使用量出典、差分、反復判定を表示する。

現行の `comparison.json` は成果不合格のペアの削減値を `null` とする。上の「全開始ランの使用量と成果を同時に扱う」仕様に向けた**成果一件あたり総トークン**と品質非劣性の群間推定は未実装である。したがって現行の `decrease` は、比較可能な全ペアが品質に合格し、かつ区間が事前閾値を超えたという限定的な判定である。複数課題を製品全体へ重み付けした結論にも使わない。

`direct` は同じ共通ランナーで成果を採点するが、プロキシ外の子・補助推論を含む総量を確認できないため差分を出さない。`xcell-locate` は最終回答に加えて独立した検索５回と読取５回の呼出 ID・結果・対象・順序を検査する。Grok Build と Devin CLI の現行ログではこの順序を証明できず、当該課題は比較不能とする。親子課題も子の使用量とモデルを帰属できない場合は比較不能とする。Grok Build のキャンセル応答と Devin CLI の Connect 応答の個別欠測をゼロとして書き換えない。
