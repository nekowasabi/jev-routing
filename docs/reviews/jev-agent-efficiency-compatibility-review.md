## 判定

**要修正。分析の方向性は妥当だが、そのままClaude Code・Grok Build共通の実装計画にはできない。**

Claude Codeにはプロキシ経由でタスクを完了した記録がある。Grok Buildにもプロキシ通過と本文削減の記録はあるが、比較タスクの完了条件を満たしていない。両者とも、提案した全工程が動作する証拠はない。

特に、HTTP要求内の結果選別と、ホストがLLMへ要求を出す回数の削減は別の変更である。前者は対応するJSON形式で実施できる。後者はホスト側の実行制御への接続が必要で、今回その接続契約は確認できていない。

## 施策ごとの実装境界

| 施策 | プロキシ内でできる範囲 | 追加で必要なもの |
|---|---|---|
| 検索・検証結果の選別 | 次のJSON要求に含まれた対応済みの結果本文を選別・縮小する | 形式と呼出しID対応、証拠の保護、入力予算、必要時の再取得。ホスト内履歴まで短くなるとは限らない |
| 待機・再試行のターン省略 | 既に送られた要求を書き換えるだけでは省略できない | ホストが要求を出す前の状態制御、承認・冪等性・期限・キャンセルの契約 |
| 指示・スキルの選別 | 要求本文の編集自体は可能 | 必須指示と任意資料の境界、明示指定の維持、ホストが管理するスキルの意味。安全な構造がなければホスト側で選択する |
| 委譲の起動・完了集約 | 候補ツールを絞ることは可能 | 子エージェントの開始・完了・中断を扱う接続。単なるツール名変換では代替できない |
| 記録・記憶 | 将来のプロキシ内ログ追加は可能 | 本格的な記憶・教訓管理は既存機能ではない。既存の記録先があればそちらを使う |
| モデル・推論量の選択 | JSONの `model` や推論設定の変更は技術的に可能 | 上流・認証・モデルが受け入れる契約、品質、キャッシュ、応答形式の検証。実行ループ変更が常に必要とは限らない |

HTTP上の結果を短縮しても、このプロキシにはホスト内部の履歴を書き戻す仕組みがない。ホスト側の文脈量表示や自動圧縮の発動まで改善すると期待する場合は、別途確認する必要がある。

## 修正後の推奨順序

1. Claude/Grokの実際の要求形式とカタログを保存した再生試験を用意する。並列ID、強制 `tool_choice`、空カタログ、推論設定、SSE・認証の透過性を含める。
2. 既存の形式・名前・情報保持・Jev入力予算の問題を解消する。現在のテスト成功だけではこれらを保証できない。
3. 最適化の適用とタスクの完了を別々に測る。単一候補・少数候補・元カタログを比較し、親子合計の使用量、キャッシュ、Jev待ち、再取得を確認する。
4. プロキシ内の不要な判定を省き、短い検索候補の選別を試す。完了品質と総費用・総時間が維持・改善する条件でのみ有効化する。
5. 待機・再試行・委譲は、Claude Code・Grok Buildそれぞれの利用可能な接続契約を確認してから、独立した実装案として判断する。

実測スクリプトは承認を省く設定を利用する（`scripts/test-x-cell.sh:45–63`）。その結果を、通常の承認付き運用で待機・再試行が安全に動く証拠にはしない。今回、公式フック仕様の網羅的な外部調査は行っておらず、接続点が未確認なことを「存在しない」とも断定しない。
